# 编码规范审查清单

以[个人编码规范](core.md)及适用语言附录为准。审查本次变更及受影响调用方，按风险选择下列项目；不要求每项新增测试或生成单独报告。

## 设计与实现

- [ ] 模块、状态、规则与权威数据有明确所有者；新增接口隐藏了有价值的复杂度。
- [ ] 主流程能从方法名称读懂；拆分按语义组织，没有新增无收益的转发层或泛化容器。
- [ ] 输入与结果区分有效空值、缺失、未知、拒绝与故障；业务分支不依赖名称猜测或错误字符串。
- [ ] 外部合同、调用方、版本约束与配置默认值已核对；契约变更具有对应迁移或协商方案。
- [ ] 错误原因保留，重试与副作用幂等匹配；部分成功与结果不确定有明确处理。
- [ ] 并发任务、队列、锁、事务与资源有清楚的生命周期、容量和退出机制。
- [ ] 关键设计的注释解释实际约束、选择原因与取舍；不是“为了性能/最佳实践”等无依据的套话。
- [ ] 关键接口及状态转换给出具体 input → output，覆盖正常与关键边界/失败；输入单位、返回/错误、状态变化与副作用可据此理解，且与实现及验证证据一致。
- [ ] 注释在适当的模块/接口/局部决策处，采用语言原生文档格式；说明足够但不逐行复述或给简单方法强套长模板。中文要求或项目语言例外明确。
- [ ] 替代路径清理完整，未误删仍有效的数据、契约或无关工作。

## 验证与交付

- [ ] 首次使用或环境变化时已核对工具实际启动、项目预期版本及配置/依赖；缺失按项目入口准备，未把 PATH 存在或版本探测成功当作项目门禁通过。见[本地执行](local-checks.md)。
- [ ] 运行了项目适用的 formatter、静态分析、编译和测试门禁；未执行项说明原因。
- [ ] 工具版本、规则、构建矩阵与 CI 入口明确；必需检查失败/超时/缺报告均未被吞掉，已接入 Sonar 时等待实际 Quality Gate。见[硬质量门禁](quality-gates.md)。
- [ ] 新增或修改的门禁有已知违规导致失败、修复后通过的证据；新增基线或豁免有具体范围、原因、责任人与复查条件，未通过削弱门禁掩盖缺陷。
- [ ] 规范已定义、项目配置、CI 运行与远端合并阻断分开报告；涉及远端接入时核对本次提交的 required checks 与适用触发条件。
- [ ] 测试验证接口行为，覆盖改动涉及的正常、拒绝、故障、边界和时序；参考结果独立于被测算法。
- [ ] 缺陷有复现与修复后的同场景证据；只通过替身测试时没有声称真实集成完成。
- [ ] 性能结论来自可比较测量，指标存在、进程健康与业务正确没有混为一谈。
- [ ] 任务文件边界清楚，既有未提交内容保留；提交、推送、部署均符合当前授权。
- [ ] 项目例外记录了覆盖条目、范围、原因和替代保证；输出中准确说明已完成阶段与验证缺口。

## 判定方式

- 正确性、外部契约、数据丢失、资源泄漏等问题必须指出具体路径、触发条件和影响，不能仅以“违背最佳实践”定性。
- 默认设计规则偏离但理由充分时接受例外；不为了统一外观提出大范围重构。
- 机械风格交给工具检查，设计建议与必须修复的问题明确区分。完成汇报只保留结论、相关证据和实质限制。
