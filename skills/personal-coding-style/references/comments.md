# 代码注释：设计原因与 input → output

用户明确要求：关键设计解释为什么这样做，并给出执行的 input → output，让读者能从注释理解调用结果。适用于所有语言；与[通用规范](core.md)一起执行。

## 1. 哪些地方必须写

| 位置 | 必要说明 |
| --- | --- |
| 关键模块/类型 | 职责、拥有的状态、不变量、依赖边界；有取舍的设计解释原因 |
| 公开接口及关键内部方法 | 输入约束、返回/错误、具体输入输出；有状态或 I/O 时说明副作用与失败后状态 |
| 非显然的分支、算法或同步点 | 为什么必须这样处理、保护什么不变量、改变顺序会有什么后果 |
| 回归/并发/故障测试 | 为什么该场景重要，输入与时序如何触发问题，预期的可观察结果 |

普通 getter、清楚的局部赋值或一次性简单函数无需机械套用完整模板。对关键实现，即使方法短，也不能因“代码看得懂”省略关键原因和合同。

## 2. 为什么这样设计

按实际需要回答“约束/问题 → 选择 → 收益和代价”。解释使用锁、缓存、幂等键、复制、后台任务或降级策略的真实原因；存在易被误选的替代方案时，简要说明它不满足什么要求。

- 写具体因果，例如“检查版本和写入在同一锁内，防止校验后被撤销消息穿插而恢复旧权限”。
- 不用“提高性能”“保证线程安全”“符合最佳实践”代替理由。性能收益需有证据；没有依据时描述设计目标与成本，不能编造历史决策或基准结论。
- 长期跨模块取舍链接项目 ADR；代码附近仍保留维护者必须知道的原因。局部决策不要求新建 ADR。

## 3. input → output 要能解释一次执行

**输入**：关键参数含义、单位/时区、有效范围、空/缺失语义；有状态的方法还包括调用前状态、版本或外部前提。

**输出**：返回值或异常/错误、调用后状态、外部副作用。异步接口区分“接收/入队返回”与“最终业务结果”；成功返回不能被注释夸大为已持久化或已投递。

**示例**：关键接口至少给一个正常路径及一个与其风险相关的边界/拒绝/失败路径。使用具体值和结果；单写“输入 Request，输出 Response”不足以帮助理解。多阶段流程可写“输入 → 校验/决策 → 副作用 → 输出”，标明失败发生在副作用前还是后。

```text
目的：一次调用负责的业务动作。
原因：实际约束 → 采用该设计 → 收益与代价。
输入：含义、单位、前置状态和必要约束。
输出：成功结果、失败结果、状态变化和副作用。
示例：具体输入及前置状态 → 返回/错误 + 后置状态。
边界：并发、幂等、取消、持久化等真正相关的保证及不保证。
```

以上是检查维度，不是每个方法都要粘贴的固定六段。无需说明的维度可以省略；隐含副作用和失败语义不能省略。公开 API 的异常、取消、线程安全等必须与实现匹配。

## 4. 注释 bad/good：同一段实现，不同的理解成本

以下是纯计算的伪代码；`available`、`requested` 均为非负整数额度，零申请合法，不修改外部余额。这里只比较注释，bad/good 的计算行为一致。

**Bad**

```text
// 计算余额。
remaining(available, requested):
    if requested > available: return Error(Insufficient)
    return Ok(available - requested)
```

**问题**：不知道为什么先比较、零值是否合法、失败代表什么，也容易把计算结果误认为已经扣减了真实余额。

**Good**

```text
// remaining 计算申请后的可用额度，不提交真实扣减。
// 原因：先比较再减法，避免余额不足被表示为负数或无符号下溢；
// 将纯判断与持久化分离，使调用方能在自己的原子边界内应用结果。
// 输入：available/requested 为非负整数额度，单位一致；requested=0 合法。
// 输出：Ok(剩余额度) 或 Error(Insufficient)；不修改输入或外部存储。
// input → output：
//   (10, 3) → Ok(7)
//   (10, 0) → Ok(10)
//   (10, 11) → Error(Insufficient)，外部余额不变
// 边界：不提供并发准入保证；共享余额的读取、判断、写入需由调用方原子执行。
remaining(available, requested):
    if requested > available: return Error(Insufficient)
    return Ok(available - requested)
```

**改善**：读者知道方案的目的、整数边界、零值与失败含义，以及返回结果不等于真实扣减。并发保证没有超出这段纯计算能力。

**何时不照搬**：若业务允许负余额或 requested 有小数，应修改合同和实现；不要用注释宣称本函数已做参数校验，非负输入在本例是调用前提。简单展示计算可缩短注释，关键并发与副作用边界保留。

**验证关注点**：正常申请、零申请、刚好耗尽、超额，以及输入对象/外部状态没有变化；这类单元验证不能代替并发原子性测试。

## 5. 语言原生注释示例

完整注释直接放在对应案例实现上方，与代码和断言一起维护；这里不另存第二份摘录。

- **Go**：[G2](cases-go.md#g2) 的 `read` 用 `//` 说明为何区分有效空值、缺失与故障，以及返回副本的原因；给出正常、缺失、失败的 input → output。导出声明注释以名称开头，关键内部方法同样写清合同。
- **Rust**：[R1](cases-rust.md#r1) 的 `approve` 用 `///` 解释为何采用独占借用；明确 `Pending + receipt → Ok + Approved`，以及终态拒绝后原事实保留，配合 `# Errors`。panic、并发与取消按实际 API 补充，不能用 Result 掩盖已发生的副作用。
- **Java**：[J2](cases-java.md#j2) 的 `Route` 用 Javadoc 解释防御性复制原因，以 `@param` / `@throws` 说明字段与错误，展示输入列表修改后对象仍保持快照。构造器也有“创建后的状态”这一输出；普通方法按需补 `@return`。

## 6. 维护与验收

- 改变函数行为、单位、边界、默认值或状态转移时，同步修改注释及示例；不保留已经失效的设计理由。
- 关键 input → output 应能对应现有测试或可复核的实现分支；纯注释变更检查语义一致性即可，不为了文档重复制造测试。
- 状态机与缓存的完整示例见 [C6](cases-design.md#c6)；有版本、幂等或取消时把这些前提写入示例输入。
- 注释中使用虚构标识与数据，不写真实凭据或个人数据；避免无主 TODO、过时提交历史和已注释掉的大段旧代码。
