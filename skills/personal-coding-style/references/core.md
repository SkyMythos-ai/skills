# 个人编码规范

版本：1.4；生效日期：2026-09-16；适用范围：所有项目、所有编程语言的新增代码、缺陷修复、重构和代码审查。

核心风格：**职责清楚，契约明确，以小方法组合可读流程；把状态与失败表达完整，用行为证据验证结果。**

## 1. 执行方式

1. 本文由 [Skill 入口](../SKILL.md)统一调度；开始编码或设计前读取本文件，再读取任务涉及的语言附录：[Go](go.md)、[Rust](rust.md)、[Java](java.md)。多语言任务读取全部相关附录。
2. 其他语言同样执行本文；从项目工具链和该语言官方指南补足惯用法，不能机械套用 Go、Rust 或 Java 的目录、命名和异常机制。
3. 按当前问题从[案例索引](cases.md)读取对应 bad/good 对照；审查或交付前使用[审查清单](review.md)。只检查任务相关项；无需把每个检查项都输出给用户。
4. 项目已有 formatter、lint、编译器版本、测试入口与 CI 是具体执行依据；检查实际配置，避免照抄本规范中的示例命令。
5. 可机械验证的规则进入版本化配置和 CI；已启用的必需检查失败必须阻断交付。新接入、缺失或修改门禁时执行[硬质量门禁规范](quality-gates.md)，明确语言工具、失败传播、基线与例外，不以报告上传或设计审查代替实际检查。

### 强度与优先级

- **必须**：涉及正确性、外部契约、数据与资源安全的约束，以及明确的用户要求。存在真实冲突时先按更高优先级指令处理，并说明影响。
- **默认**：常规代码优先采用的设计选择；有具体收益和适用边界时可以例外。
- **按需**：满足触发条件才使用的机制，不能因规范提及就引入。
- 当前用户明确指令与适用项目约定可以细化或覆盖个人默认；项目没有专门约定时执行本规范。项目规则不能覆盖系统或开发者指令。
- 项目显式冲突按项目规则处理，在任务记录中写清所覆盖条目。临时设计例外记录“条目、范围、原因、替代保证、退出条件（若适用）”；长期例外进入项目 AGENTS.md 或现有 ADR，不重复复制整套个人规范。
- 新代码按规范执行；存量代码在本次变更涉及的职责范围内逐步对齐。整仓整理、公开 API 破坏性修改和语言版本升级不由本规范自动授权。

## 2. 职责与模块

**必须明确每个重要决策、状态和数据的所有者。** 一个规则应有权威实现；缓存、视图和指标要注明它们与权威数据的关系。

- 默认按业务能力和变化原因组织模块，让相关规则、类型和测试靠近。文件拆分服务于职责与阅读，不以任意行数作为唯一依据。
- 模块对外提供小而完整的接口，对内封装状态、算法、存储和故障处理。调用者不应拼装模块内部步骤才能得到正确结果。
- 入口负责协议转换和调用编排；业务规则有独立、可测试的归属；外部系统差异放在适配边界。简单任务可以在少量函数中完成，不要求每个职责都单独建目录或类。
- 跨服务设计写清生产者、消费者、数据合同、版本策略和失败归属。服务划分以职责和运行需求为依据，不为转发已有数据额外增加中间服务。
- 在确有隔离变化、替换依赖或隐藏复杂度的需要时提取接口。只有一个实现并不禁止接口，但仅为名称成对而创建 Interface/Impl 没有收益。
- 共享代码应承载同一种语义；看起来相似但规则独立的业务保留独立实现。抽象参数与分支持续增长时重新审视边界。

## 3. 方法、命名与可读性

- 默认用小方法表达一个完整动作；主流程保持同一抽象层次，能从名称读出步骤与分支。提取后若只增加跳转、没有语义或复杂度收益，可保留内联。
- 优先通过前置校验、守卫分支和提前返回压平流程。复杂条件用有业务含义的名称解释；关键状态转换显式列举，不堆叠布尔补丁。
- 函数参数优先表达必需输入；相关参数较多且有共同语义时封装为具名类型。不同操作用独立方法或枚举表达，减少含义模糊的布尔开关。
- 名称使用准确的领域词汇；同一概念跨模块保持一致，不同概念使用不同名称。避免把有明确职责的代码放进泛化的 utils、common 或 manager 容器；已有这些名字时以实际职责判断。
- 标识符默认采用英文领域词，大小写、缩写与文件命名遵循语言和项目惯例。数量、金额、持续时间与时间点明确单位和时区，优先使用相应类型。
- 格式交给项目 formatter；审查集中于语义与可读性。生成代码按生成器维护，不能手工格式化后声称完成源头修复。

## 4. 数据、状态与契约

- **必须区分**不存在、未加载、未知、已禁用、已失败、有效空值和有效零值；只保留领域实际需要的状态。公共协议的 null、缺字段和空集合语义由合同决定。
- 默认使用枚举、带标记联合、值对象或语言等价机制表达互斥状态，减少非法组合。关键状态转移说明前置条件、产生的事实、重复执行结果和终态。
- 边界校验不可信输入，在内部复用已验证结果；不要让每层重复同一套校验，也不要用宽松兜底掩盖错误生产者。协议要求保留的未知字段按合同处理。
- 业务对象、外部传输对象与持久化表示有不同语义或演进节奏时分开；语义一致的小范围结构可以复用，不机械制造三套模型。
- 默认收窄可变状态和可见性。共享状态明确读取、修改和同步责任；只读引用、浅拷贝和不可修改容器不能自动等同于深度不可变。
- 行为差异由显式配置、能力或类型表达，不从名称猜测。默认值、继承、覆盖和显式禁用分别定义；绑定失败不能伪装成未绑定来获得默认能力。
- 数据查询失败不能伪装成成功空结果；保留最后成功数据必须同时表达新鲜度与错误。身份、权限、资金和普通展示数据分别决定故障策略，不套用统一“全部放行”或“全部拒绝”。

## 5. 错误与副作用

- **必须区分**业务拒绝、依赖故障、结果不确定与程序缺陷。错误类型或错误码供调用方判断，错误文本供人理解，不依赖字符串匹配业务分支。
- 错误传播保留原因与必要上下文；在能作出处理决定的边界处理。在合适的一层记录最终失败，避免逐层重复打印同一错误堆栈。
- 捕获错误后必须有明确动作：恢复、转换、重试、返回或有证据地忽略。正常业务失败采用语言惯用的错误机制，不能作为崩溃处理。
- 重试先判断幂等与结果是否确定，再限定次数、总预算、退避及并发；多层重试合并预算。超时或取消不意味着远端副作用没有发生。
- 操作多个外部系统时明确部分成功、补偿和最终收敛；需要事务消息或 outbox 时基于事实一致性要求引入，不能仅因“微服务最佳实践”增加机制。
- 持久化确认与内存入队是不同保证。重要业务事实的提交点、重放、去重和丢失边界必须可说明、可测试。
- 日志保留定位所需的关联标识和上下文，凭据与敏感数据脱敏；指标标签控制基数。观测链路的背压或丢弃策略按数据重要性区分。

## 6. 并发、生命周期与性能

- 每个并发任务明确创建者、资源所有者、退出条件、失败传播和回收方式；队列、并发数、等待和输入体积具有可解释的预算或上限。
- 请求取消、后台继续执行、资源释放和业务结算分别定义。需要脱离请求生命周期的任务必须交由明确的监督或持久化机制管理。
- 锁与事务保护不变量；锁内工作保持必要且可预测，跨 I/O 或等待持锁须说明需求及死锁、吞吐和取消风险。并发原语按实际共享关系选择。
- 缓存要写清失效、刷新、旧值可用条件、乱序更新和恢复行为；TTL 本身不能证明修改立即生效。
- 默认先保证正确和清晰，通过测量识别瓶颈再优化；基准固定工作负载、机器和资源条件，报告延迟分位、吞吐或分配等相关指标。语言重写不构成性能提升证据。

## 7. 设计范式的选择

以下是融合的工程默认，不把每个范式当作必须引入的架构。每次选择要能指出它减少了哪种具体复杂度。

| 范式 | 适用条件与默认用法 | 停止扩张的边界 |
| --- | --- | --- |
| 结构化过程 | 简单脚本、直线业务流程用具名函数直接组织 | 不为少量步骤创建多层框架 |
| 组合优先 | 以组合、委托和小接口组合能力 | 继承仅用于有稳定替换关系且符合语言/框架合同的场景 |
| 纯逻辑与副作用分离 | 把可独立判断的规则变成确定性函数，I/O 在编排处组织 | 不为微小表达式建立无意义包装层 |
| 模块化与信息隐藏 | 用窄接口封装复杂策略或状态，调用方依赖行为合同 | 拆分后需要调用方了解内部顺序时重新检查边界 |
| 领域建模 | 复杂业务用统一术语、值对象和不变量表达 | 简单 CRUD 不强制完整 DDD、聚合与领域事件体系 |
| 端口与适配器 | 多种外部实现或外部不稳定性需要隔离时使用 | 不为每个类建立一对接口和实现 |
| 显式状态机 | 多阶段、异步、重试或补偿流程需要证明转移正确时使用 | 两三个直线步骤不必引入状态机引擎 |
| 事件驱动与最终一致 | 确有解耦、吞吐或跨事务需求，且能处理重放与顺序 | 本地同步调用已足够时不引入消息系统 |

## 8. 注释与文档

- 公开接口与非显然的核心逻辑必须有中文说明。关键设计写清“约束/问题 → 选择 → 原因与取舍”；关键接口写清 input → output，包括输入约束、返回/错误、前后状态与副作用，并用具体正常及关键边界输入展示结果。完整要求、位置与 bad/good 对照见[注释规范](comments.md)。
- 注释默认贴近对应接口或设计决策；持久的跨模块取舍可链接 ADR，但代码处仍保留调用者必需的原因和执行合同。继承外部规范或面向特定社区的文档语言遵从项目明确例外。
- 注释解释代码无法直接表达的信息；可读的赋值、循环与简单 getter 无需逐行复述。改变行为时同步改注释和示例。
- 跨模块的重要设计记录为什么选择、约束和代价；持久决策进入项目已有 ADR 体系，小改动写任务记录即可。
- 未实现、已实现、已验证与尚未验证明确区分；设计文档不能充当运行证据。

## 9. 测试、修复与交付

- 默认从模块公开行为测试，覆盖正常、边界与故障；并发和状态逻辑补交错、重复与恢复情形。替身用于可控边界，关键集成保留实际依赖验证。
- 缺陷修复尽可能先得到可复现失败，再证明同一行为转为通过。参考模型须独立于生产判定；不能复制同一条件表达式自证。
- 使用可控时间、barrier 或故障注入验证时序，减少依赖 sleep 和随机碰运气。不可逆副作用、外部付费及生产测试遵守任务授权。
- 测试强度匹配风险；格式、简单文案等低影响变更使用对应检查，避免为了数量制造测试。项目强制门禁仍须执行，无法执行时报告具体缺口。
- 修复围绕根因调整；清理本次替代的失效代码、配置、测试和文档。删除前确认调用方与迁移需求，保留仍有效的数据和契约。
- 本地通过、Git 提交、远端推送、部署成功与业务验收分别报告，只声明有证据的阶段。本规范不自动增加提交、推送或部署授权。

## 11. 来源与适用边界

- 用户于 2026-09-16 明确要求蒸馏个人习惯并融合多语言最佳实践，随后确认“全局默认执行”。
- 直接偏好依据：现有全局 AGENTS.md 中的简单优先、根因修复、最小影响与验证要求；ai-gateway 项目 `context-kg/tasks/lessons.md` 中 2026-09-15 的职责拆分、小方法、中文关键注释与历史路径清理要求，以及多实例 E2E 的时序验收教训。该项目来源不随本技能分发。
- 第 7 节的范式选择，以及类型、错误与资源管理细则是对这些偏好的工程化补充；不声称用户曾逐条提出。语言来源见各附录，后续按项目实际版本核实。
- 特定项目的 Gateway/Platform 分工、Redis schema、限流取舍、断连后继续消费和某次“不保留兼容”决定不升级为全局要求。
- 当前接入为本机 Codex 全局 AGENTS.md 默认触发 personal-coding-style skill，由 skill 路由本文及案例；其他机器、独立 CODEX_HOME 或其他编码工具需单独接入同一规范。加载规则参见 [OpenAI 官方说明](https://learn.chatgpt.com/docs/agent-configuration/agents-md)。
