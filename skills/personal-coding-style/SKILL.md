# 个人编码风格

目标：职责清楚、契约明确、主流程可读，状态与失败完整，结果有行为证据。全局默认执行；具体编码保持语言惯用法。

## 开始工作

1. 读取[通用准则](references/core.md)，核对本次用户要求、适用项目约定与实际工具链。已在本轮上下文读取且未更新时复用。
2. 按涉及语言读取 [Go](references/go.md)、[Rust](references/rust.md)、[Java](references/java.md)；其他语言按通用准则和项目/语言官方惯例处理。
3. 从[案例索引](references/cases.md)选择与当前问题相符的案例，读取对应完整案例段。普通实现与审查只读相关案例；解释规范、评估取舍或发生同类纠正时，必须用具体代码对照说明，不能只复述“单一职责、最佳实践”。
4. 涉及关键接口、状态转换、并发/幂等/降级设计，或编写与审查注释时，读取[设计原因与输入输出注释规范](references/comments.md)。注释让读者理解为什么选择该方案，以及具体 input → output、前后状态和副作用。
5. 编码任务核对项目真实检查入口；涉及新项目、工具链/CI 变更、门禁缺失或失败、质量策略设计时，读取[语言检查与硬质量门禁](references/quality-gates.md)。按语言配置 formatter、linter、编译与测试；已接入 Sonar 时等待实际 Quality Gate，不把上传报告当作通过。
6. 工具首次使用、环境变化、工具缺失或用户询问本地可执行性时，读取[本地环境准备与探测](references/local-checks.md)，按需运行 `scripts/probe_tools.py`。复用项目版本声明和 setup/check；工具能启动后仍须运行真实项目门禁。

进入编码前应能说明本次改动的职责、合同、失败语义和验证方式；简单修改用一句话或内部检查完成，不生成无收益的架构文档。

## 按任务执行

- **实现/修复**：让主流程以领域动作组织；状态、错误、资源与副作用有明确归属。使用实际复现或合同验证改动，避免照搬案例的业务策略。
- **重构/设计**：先固定外部行为与不变量，再调整内部边界。具体说明抽象降低的复杂度，清理本次替代路径；接口、DDD、状态机与事件机制按触发条件采用。
- **代码审查**：用[审查清单](references/review.md)检查变更及调用方。问题必须附位置、触发条件、影响和改法；默认设计偏好与正确性缺陷分开，不要求存量整仓对齐。
- **规范说明/更新**：每个新增的非显然规则给出场景、bad、问题、good、改善点、适用边界与验证关注点。延续可检索的案例 ID；小改动只完善相关例子，不复制整套文档。

用户要求讲解某条规范时，答复中直接展示一组最小的 bad/good 代码对照，并指出为何改、何时不适用；只读了案例或只展示 good 不算完成讲解。普通实现任务无需在最终答复重复整组示例。

缩短案例时保留结论依赖的关键步骤和前提；省略实现就收窄保证。例如仅写一个通知 worker、却没有可靠入队步骤，不能声称通知可恢复或事务消息完整。

## 约束与完成标准

- 当前用户要求与适用项目约定优先于个人默认；例外记明条目、范围、原因和替代保证。普通选择不需要反复请求确认。
- 小方法、组合、显式状态是设计手段，不按方法数或文件行数机械拆分；已有稳定代码不因偏好不同就强制重写。
- 案例是边界明确的教学程序或标明的伪代码，不是生产模板。未示范的认证、持久化、分布式原子性等保证必须由实际项目证明。
- 交付时对应本次风险报告验证结果与缺口。格式/文案变更使用相关检查，项目已有强制门禁仍执行。
- 必需门禁失败不得当作完成；新接入检查要证明违规会导致非零退出。分别报告规范、配置、CI 执行及远端合并阻断的实际阶段，遵循[门禁执行合同](references/quality-gates.md#执行合同)。
- 修改语言案例后运行 `python3 scripts/verify_examples.py`，可用 `--language go`、`rust` 或 `java` 限定范围。脚本只编译 bad、编译并执行 good 中的断言；它不证明生产集成，缺失工具链返回未完成状态。
- Go 并发案例可加 `--race`；本机没有 JDK 时可用 `--java-image <已在本地的JDK镜像>`。容器模式只挂载临时案例目录、禁用网络且不自动拉取镜像；选择运行环境遵守当前任务授权。
